# AI 审核联动标签体系 · 设计方案

> 状态：**设计稿（未实现）**。实现前再评审一轮，按阶段推进。
> 说明：本文件从「标签体系」起步，已扩展为**内容生态与商业化完整计划**（标签 / 公开广场 / 举报 / 付费解锁 / 邮箱通知 / 造图机器人 / 提现）。下文按模块分章，第十章起为对外展示与商业化。

## 一、结论

在现有审核链路上扩展输出标签，**改动成本低、收益高**：审核已经调用了视觉模型，让它在同一次请求里多返回 `tags` 字段即可，不增加调用次数。
关键在于**标签必须受控**（否则不可检索、不可统计），以及**双存储**（JSON 快展示 + 关联表快查询）。

## 二、标签体系设计

### 2.1 维度（受控）

| 维度 | 说明 | 示例 |
|---|---|---|
| 主体 | 图里是什么 | 人物 / 动物 / 风景 / 建筑 / 物品 / 文字截图 / 插画 / 表情包 |
| 风格 | 画面风格 | 写实 / 二次元 / 3D / 像素 / 摄影 / 手绘 |
| 用途 | 对用户的价值（图床场景最有用的维度）| 壁纸 / 头像 / 表情 / 素材 / 参考图 |
| 色调 | 画面色调 | 深色 / 亮色 / 多彩 / 单色 |
| 质量 | 可用性 | 清晰 / 模糊 / 低光照 / 有水印 |

### 2.2 数量与结构

- **默认每次 5 个**（1 主类 + 4 辅助）；数量做成设置项，可调（1~8）
- **设置项位置：模型设置 → 审核策略**（与「图片审核开关 / 协同模式」同排），字段名 `audit_tag_count`
  - 理由：标签数量是**审核输出行为的参数**（直接进审核 prompt），属于模型设置，不是站点基础配置（站点设置）、也不是用户权限（策略组）
- 主类（主体）**必选**，其余可空

### 2.3 词表：**自生长（AI-driven）**，不写死数量

**原则**：词表不封顶、不靠人工逐个添加。模型自由产出 → 系统自动登记 → AI 归并同义 → 后台可视化治理。

| 环节 | 机制 |
|---|---|
| 产出 | 审核模型每次返回 N 个中文短词（≤10 字，禁身份/人脸类） |
| 归一化 | 小写、去空格、去标点；长度截断 |
| 匹配 | 先精确匹配 `tags.name`，再匹配 `tag_aliases.alias`；命中 → 复用 + `use_count++` |
| 新词登记 | 未命中 → 自动建 tag（`source=auto`，可配「自动登记/待确认」） |
| **同义归并** | 新词出现时**采样调用轻量 LLM**：「这些新词与已有标签中哪些同义？」→ `auto` 模式自动合并（新词记为 alias），`manual` 模式进后台待确认队列 |
| 淘汰 | `use_count` 低且 90 天未使用 → 自动 `archived`（不删除，历史关联保留） |
| 治理 | 后台「标签管理」页：合并/改名/改类别/停用/批量，待确认队列可视 |

**相关设置项**（模型设置 → 审核策略）：

| 键 | 默认 | 说明 |
|---|---|---|
| `audit_tag_count` | 5 | 每次生成标签数（1~8）|
| `audit_tag_auto_register` | 1 | 新词自动登记（0=进待确认）|
| `audit_tag_merge_mode` | auto | 同义归并：auto=AI 自动 / manual=人工确认 |

**为什么这不是「死词表」**：图越来越多，词自然生长；AI 负责查重与归并；后台只做兜底治理。60 个词只是冷启动基线，不是上限。

### 2.4 不该生成什么

- **人物身份/人脸特征**（隐私风险）——只描述客观内容（"人物"、"合影"），不出"某人名字/性别/年龄"
- 政治敏感、色情暗示词——审核已有 verdict 负责拦截，标签不承担裁决

## 三、存储设计

```
images
  + tags        JSON    ["猫","插画","壁纸"]       ← 列表/API 直出，避免 JOIN

tags                                            ← 标签字典（自生长）
  id, name(唯一), slug, category(主体/风格/用途/色调/质量/未分类),
  source(auto|user|admin), status(active|pending|archived),
  use_count, first_seen_time, last_used_time, create_time

tag_aliases                                     ← 近义归并映射（AI 生成 + 人工确认）
  id, tag_id, alias(唯一), source(auto|admin), create_time

image_tags                                      ← 关联表（筛选/统计 JOIN）
  id, image_id, tag_id, source(auto|user), confidence, create_time
  UNIQUE(image_id, tag_id)
```

**为什么双写**：JSON 供列表与 API 零 JOIN 输出；关联表供「按标签筛选图片」「标签排行榜」「某标签的拒绝率」等统计。

## 四、展示位置（按优先级）

| 位置 | 形式 | 说明 |
|---|---|---|
| 后台图片管理 | 新增「标签」列（chips，最多 3 个 + 悬停全量）；筛选栏加标签筛选 | 管理员日常使用主场景 |
| 后台审核 tooltip | 在模型描述下追加 `标签：猫 / 插画 / 壁纸` | 与现有复审原因同一浮层 |
| 前台我的图库 | 卡片底部 chips | 用户侧可见，可点击筛选同标签 |
| 图片详情页（规划中）| 完整标签 + 相关推荐 | 与图片详情页一起做 |
| API 响应 | `data.tags` 数组 | Lsky 兼容不受影响（扩展字段）|
| 后台统计页（规划）| 标签排行榜 / 标签×拒绝率 | 运营决策依据 |

## 五、标签的最大化利用

1. **检索**：`/gallery?tag=猫`、后台「按标签筛选」、API `list?tag=猫`
2. **运营洞察**：标签排行榜（平台最热的图片类型）→ 指导公告/活动/内容推荐；标签×拒绝率 → 找出容易违规的标签组合，反哺审核 prompt 与词表
3. **推荐**：详情页「同标签图片」；图库「你可能喜欢」
4. **SEO**（远期）：图片详情页标签作为关键词、生成标签聚合页
5. **广告定向**（远期）：某类内容页展示对应广告位内容
6. **数据资产**：CSV 导出增加 tags 列（图片导出已有，扩一列即可）
7. **人工修正（主动学习）**：用户/管理员可增删标签 → `source=user` → 用于词表优化与模型 prompt 迭代
8. **容量治理**：标签驱动的批量操作（如"批量冻结所有『低质量』标签的图"）

## 六、实施阶段

| 阶段 | 内容 | 依赖 |
|---|---|---|
| **P1** | 审核 prompt 扩展 tags（数量读 `audit_tag_count`）+ 自生长登记 + `images.tags` JSON + 后台标签列/筛选 + API 返回 + 归一化 | 无（当天可完成）|
| **P2** | `tags`/`tag_aliases`/`image_tags` 三表 + 双写 + **AI 同义归并（采样）+ 待确认队列** + 后台「标签管理」页 + 统计页（排行榜/拒绝率） | P1 |
| **P3** | 前台图库 chips + 标签筛选页 + 用户手动修正 + 冷启动基线词表（约 60 个作为初始种子，非上限）| P2 |
| **P4** | 详情页相关推荐 / SEO 聚合页 / 广告定向 / 主动学习闭环 | P3 + 详情页 |

## 七、风险与对策

| 风险 | 对策 |
|---|---|
| 模型标签幻觉/漂移 | 受控词表 + temperature 0 + 非法标签直接丢弃 + 每次记录原始输出到审计日志 |
| token 成本增加 | prompt 增加约 30~50 tokens，可忽略；单请求不增加调用次数 |
| 多语言不一致 | 存储统一中文，展示层可映射（词表带 aliases） |
| 旧图无标签 | 后台「批量补标签」任务（复用审核链，分页回填，限流）|
| 隐私与合规 | 禁止生成身份/人脸特征类标签（见 2.4）|
| 标签噪音过多 | P2 起提供词表合并/停用工具；use_count 低的自动归档 |
| 自生长失控（新词爆炸）| 新词走归并检查；同义自动合并；待确认队列兜底；月度导出词表人工抽查 |

## 八、本期不做

- 不做标签的自动聚类/向量检索（成本与复杂度高，标签足够用）
- 不做用户自定义标签公开词表（先内部词表，P3 再放开用户修正）
- 不做基于标签的计费/权限（与 Token 计划无关）

## 十、标签的对外展示：从「私人图床」到「图片广场」

> 标签打出来只在后台看，价值只发挥了 10%。真正的价值在于**对外展示 → 检索 → 流量 → 转化**。
> 但有一条铁律：**图床默认私密，公开必须由用户显式授权**——否则直接踩隐私红线。

### 10.1 展示形态（四层，由内向外）

| 层 | 形态 | 承担职责 |
|---|---|---|
| L1 **单图详情页** `/p/{id}` | 大图 + 标签 + 相关推荐（同标签）+ 上传时间/尺寸 + 复制外链 | 最小展示单元；SEO 落地页 |
| L2 **标签聚合页** `/tag/{name}` | 该标签下全部公开图（瀑布流）+ 标签介绍 + 相邻标签 | 浏览与检索入口；SEO 主力 |
| L3 **图片广场** `/explore` | 全站公开图瀑布流，排序：最新 / 最热 / 随机；顶部热门标签 chips | 首页级别的流量承载体 |
| L4 **用户展位**（远期）| 「XX 的公开图集」个人主页 | 社区属性，需防滥用，最后做 |

### 10.2 隐私与合规红线（先于功能）

1. **默认私密**：`images.is_public=0`，公开必须用户主动操作；**支持四种粒度**：
   - 单张公开 / 单张私密
   - 批量公开 / 批量私密
   - **全部公开**（存量一次性转公开）/ **全部私密**（一键收回）
   - **自动公开**（用户级开关 `users.auto_public`：开启后存量+未来上传全部自动公开；敏感场景建议默认关）
   - 策略组可配「是否允许自动公开」「是否允许公开」
2. **只允许过审图公开**：`audit_status=pass` 才能设为公开；复审/拒绝不可公开
3. **匿名选项**：公开时可选择不显示上传者（默认匿名）
4. **随时下架**：用户取消公开即时生效；管理员可强制下架
5. **策略组开关**：「是否允许公开」「是否允许自动公开」做成策略组权限
6. **管理员下架不可再上架**：`images.ban_public=1` 后用户即使点公开也拒绝（提示「该图已被管理员下架」）；仅后台管理员可解除
7. **举报入口**：公开页必须有举报按钮；**举报权限按策略组**（策略组字段 `can_report`，如默认仅注册/VIP 可举报，游客不可）+ 后台处理队列
8. **版权提示**：公开时勾选「我拥有该图片的合法权利」

### 10.3 排序与推荐（标签直接驱动）

- 「最热」= 浏览/复制外链次数加权（新增 `images.view_count`）
- 「相关推荐」= 同标签交集排序（标签越多重叠越准）
- 「热门标签」= `tags.use_count` 结合公开图数量
- 禁止纯时间线（容易变垃圾场）；数据不足时用「随机 + 人工精选」兜底

### 10.4 商业化结合

- 公开页挂广告位（非 VIP 浏览可见，免广告组不显示）
- VIP 特权：公开图优先上广场、专属展位
- 流量飞轮：公开图 → 搜索引擎收录 → 访客 → 注册/付费转化
- **注意**：公开图外链流量纳入存储/流量治理（已有配额维度可扩展）

### 10.5 实施阶段

| 阶段 | 内容 | 前置 |
|---|---|---|
| **S1** | 图片详情页 `/p/{id}`（仅本人可见自己的私密图；公开图任何人可见）+ 「公开/私密」开关 | 标签 P1 |
| **S2** | 标签聚合页 `/tag/{name}` + 图片广场 `/explore` + 热门标签 + 举报按钮 | S1 |
| **S3** | 用户展位、相关推荐算法、SEO（sitemap/结构化数据）| S2 |
| **S4** | **举报体系（AI 初审）**：举报表 + 举报权限 + AI 判定 + 后台队列 | S2 |
| **S5** | **防盗与付费解锁**：右键禁用/预览降级/站币/解锁/分成/流水 | S4 + 支付体系 |
| **S5b** | **提现体系**：支付宝信息绑定 / 申请 / 后台审核打款 / 流水 | S5 |
| **S6** | 点赞/收藏（可选，慎重评估社区成本）| S5 |

### 10.6 风险提示

- **内容平台化 = 审核压力上升**：AI 审核（已有）兜底为主，举报+快速下架为辅
- **国内运营合规**：公开内容需具备举报、下架、日志留存能力；备案与内容安全责任在运营方
- **存储与流量成本**：公开图被大量访问，需依赖已有的配额/流量治理维度
- **不做**：不做评论区（成本远高于收益）、不做图片盗链收割、不做用户间私信
### 10.7 举报体系（AI 初审 + 人工复核）

**流程**（复用现有审核链）：

```
用户举报（图片 + 理由 + 可选截图）
  → AI 二次审核：把「举报理由 + 图片」交给审核模型，独立判定「举报是否成立」
  → 判定成立（高置信）：自动下架（is_public=0 + ban_public=1，违规图同时冻结外链）
  → 判定不成立：驳回，通知举报人
  → 拿不准：进后台人工队列
  → 后台「举报管理」：全部举报记录 + AI 判定 + 处理结果，管理员可复核/推翻（恢复公开需管理员手动解除 ban_public）
```

**下架动作分级（后台设置项 `report_action`，默认「仅下架」）**：

| 选项 | 效果 |
|---|---|
| **仅下架**（默认）| 从广场隐藏（is_public=0），**用户自己的外链仍有效**（私人使用不受影响）|
| **下架 + 冻结外链** | 等同删除：外链 404、用户自己也不能再用 |

> 逻辑：图片进站已过 AI 审核，公开后被举报多因"公开场景不合适"而非绝对违规——所以默认只下架；后台可改为"下架+冻结"从严处置。

**表结构**：
```
reports: id, image_id, reporter_user_id, reason, status(pending|ai_confirmed|ai_rejected|manual|closed),
         ai_verdict, ai_detail, handled_by, create_time, update_time
```

### 10.7b 违规指纹库（防马甲重传 · AI 前置匹配）

**背景**：管理员下架 / 举报下架的图片，用户换个账号重新上传怎么办？

**设计**：
```
banned_fingerprints: id, image_id(来源), sha1(精确), phash(感知哈希), reason,
                     source(admin|report), hit_count, create_time
```
- **上传第一步匹配指纹**：SHA1 精确命中 → 直接拒绝；**pHash 汉明距离 ≤ 5** → 判定"疑似违规图"直接拒绝（AI 前置，无需等模型审核）
- **违规累计**：`users.violation_count`，同一用户触发 N 次（`settings.violation_autoban`，默认 3）→ **自动停用账号** + 写入 audit_logs，后台可查看/重置
- 后台「图片管理」增加「加入违规指纹库」按钮（下架时自动加 + 手动补充）
- 跨账号识别（IP/设备指纹）作为远期项，涉及隐私需谨慎

### 10.7c 举报风控与通知（沿用）

**风控**：
- 同一用户恶意举报比例过高（如 30 天内 5 次被驳回）→ 自动降低其举报权重/封禁举报权
- 举报权限按策略组 `can_report` 控制（游客默认不可举报）
- AI 判定结论写入 audit_logs，可追溯

### 10.8 防盗与付费解锁（作者共盈）

**防盗措施（后台逐项开关，默认只保护付费图；开源用户可自行改为全站限制）**：

| 开关 | 默认 | 说明 |
|---|---|---|
| `protect_paid_only` | 1 | 仅对设置了付费的图做限制（免费图不限制）|
| `block_right_click` | 1 | 禁止右键保存 |
| `block_drag_save` | 1 | 禁止拖拽保存 |
| `block_long_press` | 1 | 禁止移动端长按 |
| `preview_degrade` | 1 | 付费图预览降级（低清 + 水印）|
| `watermark_paid` | 1 | 付费图加水印 |
| `invisible_watermark` | 0 | 隐形水印（作者 ID 隐写，泄露溯源）|
| `referer_whitelist` | 0 | 防盗链 Referer 白名单（基于代理模式）|

> 开源场景：别人部署时可以关闭 `protect_paid_only`，对全站图片限制；也可以全关，完全开放。

**共盈模式**：

| 角色 | 机制 |
|---|---|
| 站点货币 | 站币（credits）：支付通道充值 + 签到/任务赠送 + VIP 赠送 |
| 作者定价 | 单图解锁价格（站币）/ 月卡（VIP 免费下全站）/ 商用授权（可选加价档） |
| 分成 | 默认统一比例（如 平台 30% / 作者 70%）；**可开启「按图片来源区分」**：AI 生成图（模型成本由平台承担）作者比例较低（如 50%），用户自制上传（真实创作）比例较高（如 70%）。设置项：`revenue_split_mode`（0=统一 / 1=区分）、`share_ai`、`share_user`；图片标记 `images.origin`（upload/api/user_gen/gen_bot）|
| 账务 | `users.credits` 余额 + `credit_logs` 流水 + `unlocks` 解锁记录（防重复扣费看这里） |
| 风控 | 退款扣回、下架自动退款、最低提现门槛、异常解锁监控 |

**为什么这套能提高质量**：付费图必须过审 + 有标签 + 有浏览量，创作者为了收益会主动上传高质量内容；推荐算法按下载/解锁量加权 → 优质内容上浮。

**风险**：提现的税务与合规（远期需明确）、盗链截图无法完全防（隐形水印兜底）、初期内容不足需运营精选冷启动。
### 10.8b 提现体系（作者收益兑现）

**用户侧**：
1. 个人中心 → 「收益钱包」：余额（站币）、累计收益、待结算、提现记录
2. **提现设置**：绑定支付宝收款信息（真实姓名 + 支付宝账号，仅用于打款）
3. **申请提现**：填写金额（≥ 最低提现额，如 50 元）→ 提交 → 状态「待审核」
4. 到账后状态变「已打款」+ 邮件通知（消费类通知矩阵中的「分成结算」）

**后台侧**：
- 「提现管理」页：待审核列表（用户/金额/支付宝信息/申请时间）、通过/驳回（填原因）、**标记已打款**（填转账凭证号）
- 最低提现额、手续费率（如 0% 或 2%）、每月提现次数限制——均为设置项
- 风控：新绑定支付宝后 T+7 才能提现；异常提现（短时间多笔）标记人工审核；被举报/违规用户的收益冻结

**表结构**：
```
users: + alipay_name, alipay_account, credits(余额), credits_total(累计收益)
withdrawals: id, user_id, amount, fee, real_amount, alipay_name, alipay_account,
             status(pending|approved|paid|rejected), remark, voucher_no,
             handled_by, create_time, update_time
credit_logs: id, user_id, type(unlock|share|withdraw|adjust), amount, balance_after,
             ref_id, remark, create_time
```

**打款方式**：
- **P0：人工打款**（后台标记已打款 + 凭证号）——无需资质，绝大多数自建站的标准做法
- 远期：支付宝开放平台「转账到支付宝账户」API 自动打款（需企业资质与签约，列为可选增强）

### 10.9 内容自动化：造图机器人（定时定量填充图库）

**目标**：解决冷启动没内容的问题；同时作为文生图模型的**持续验收通道**（先自己跑通，再给用户用）。

**机制**：
```
后台「内容任务」→ 新建任务：
  名称 / 提示词池(JSON 多组) / 图片类别 / 每次生成数量 / 执行间隔 / 生成模型(选生成模型卡片)
  / 目标上传账号(种子账号) / 是否自动公开 / 开关
→ 定时任务(每5分钟扫描到期) → 调生成模型 /images/generations
→ 生成图片存入临时区 → 走完整 UploadService（审核+标签+存储，不绕通道）
→ 审核通过 → 按任务配置自动公开 → 进广场
```

**表**：`gen_tasks`（任务配置 + last_run/next_run/统计）、`gen_task_logs`（每次执行：生成数/成功数/失败原因/耗时）

**风控与成本**：
- 单任务单日总量上限；模型调用费用记入日志
- **生成去重**：pHash 与已有图比对，近重复丢弃（防 prompt 池单一导致重复）

**pHash 的计算与使用范围（重要设计说明）**：

| 环节 | 策略 |
|---|---|
| 计算 | **每张上传图都计算并存 pHash**（约 50ms/张，一次计算终身可用）——同时服务违规指纹匹配、机器人去重、未来相似推荐 |
| 违规库匹配（拒绝）| **永远开启**，安全刚需，不可关 |
| 造图机器人去重（丢弃）| **默认开启**，可后台关 |
| 普通用户上传近重复 | **默认不拒绝**（不同用户使用同一素材是正常需求），仅记录；后台开关 `dedup_on_upload` 可改为拒绝 |
| 结论 | 全量算指纹，但"拒绝"只发生在违规库与机器人两个场景——既安全又不干扰正常用户 |

**三个开关（后台可勾选，全部默认按此配置）**：

| 开关 | 默认 | 作用 |
|---|:---:|---|
| `banned_match_enforce` | **开** | 上传匹配违规指纹库即拒绝（安全刚需，可关但不建议）|
| `dedup_gen_bot` | **开** | 造图机器人近重复丢弃 |
| `dedup_on_upload` | 关 | 普通用户上传近重复是否拒绝 |
- 种子账号在 `users` 标记 `is_seed=1`（公开页可显示"官方内容"徽章）
- 生成失败自动暂停任务并告警（后台提示）

**为什么放这里而不是单独做**：这条链路的每一步（生成/审核/标签/公开）都是现有能力，组合即用；先内部跑稳，再开放给用户文生图页面。

### 10.10 实施顺序（完整版）

标签 P1 → S1 详情页+公开（含自动/全部/ban_public）→ 标签 P2（词表三表+归并）→ S2 广场+标签页 → S3 SEO/推荐 → **S4 举报（AI 初审+指纹库+违规累计停用）** → **S5 付费解锁+防盗开关矩阵+分成** → **S6 造图机器人（内容自动化）** → S7 点赞收藏（可选）

## 十一、邮件体系（P0 优先级）

> 邮箱是后续所有功能的通知底座：注册验证、找回密码、审核/下架通知、举报处理、分成结算、违规警告——全部依赖它。
> **结论：邮箱配置是下一个开工项（标签 P1 之前）**。

### 11.1 SMTP 配置（后台）

新增「邮件设置」页（或并入站点设置）：

| 字段 | 说明 |
|---|---|
| SMTP 服务器 | 如 smtp.qq.com / smtp.163.com |
| 端口 / 加密 | 465（SSL）/ 587（STARTTLS）|
| 账号 / 密码（授权码）| 发件邮箱 |
| 发件人名称 | 如「逍遥图床」|
| **测试发送** | 输入收件地址即时验证配置 |

实现：PHPMailer（composer，已符合「能用现成不造轮子」）；发送日志 `mail_logs`（收件人/模板/状态/错误）便于排障。

### 11.2 注册与验证策略（可配）

`verify_mode`（站点设置）：

| 模式 | 行为 |
|---|---|
| **none** | 不验证邮箱，注册即用（默认，适合内网/自用）|
| **register** | 注册后需点击邮件链接验证才能**登录**（严格）|
| **lazy** | 注册即可登录，但**上传/公开/举报等核心操作前必须验证邮箱**（推荐：转化与安全平衡）|

补充：`verify_expire`（验证链接有效期，默认 24h）、`resend_interval`（重发间隔，默认 60s）。

### 11.3 通知矩阵（事件 × 接收方 × 开关）

**分级原则**：
- **交易类**（花钱/收益相关）：最高优先级，**必发不可退订**（合规惯例：账单与交易凭证）
- **安全类**（验证码/密码）：必发
- **运维类**（站点告急）：发管理员
- **运营类**（公告/推荐）：可订阅

| 事件 | 用户 | 管理员 | 默认 | 阶段 |
|---|---|:---:|---|---|
| 邮箱验证 / 找回密码 | ✅ | - | 必发 | P0 |
| **存储告急**（磁盘剩余 / 配额剩余 / 网盘空间低于阈值）| - | ✅ | 开 | P0 |
| **VIP 购买成功** | ✅ | ✅ | 开 | P0 |
| **VIP 到期提醒**（提前 3 天 + 当天）| ✅ | 可配 | 开 | P1 |
| **付费图片被购买**（通知作者：谁买了 / 收益多少）| ✅ | 可配 | 开 | 随付费体系 |
| 审核拒绝 | ✅ | - | 开 | P1 |
| 举报处理结果 | 双方 | 可配 | 开 | 随举报 |
| 管理员下架 | ✅ | - | 开 | 随举报 |
| 违规警告 / 自动停用 | ✅ | ✅ | 开 | 随指纹库 |
| 分成结算（月度/提现）| ✅ | ✅ | 开 | 随付费体系 |
| 广告位购买 / 到期（规划中）| ✅ | 可配 | 占位 | 随广告升级 |
| Token 用量提醒（达上限 / 封停，仅提醒不含计费）| ✅ | - | 占位 | 随 Token 计划 |

**实现**：后台「通知设置」页 = 上表逐行开关（用户/管理员两列 checkbox）；`settings.mail_events` JSON 存储。

### 11.3b 存储告急阈值（管理员通知）

```
alert_disk_free_gb   = 10     # 本地磁盘剩余低于此值 → 告警
alert_quota_left_pct = 10     # 存储配额剩余低于百分比 → 告警
alert_space_left_pct = 10     # 网盘空间剩余低于百分比 → 告警
```
- 定时任务每小时检查（think 命令 + 计划任务）
- **告警去重**：同一实例同一指标 24 小时内只发一封，恢复后重置
- 恢复通知：指标回到安全线以上发一封「已恢复」（可关）

### 11.4 模板与限流

- `mail_templates` 表（key/标题/正文，支持变量 `{{site}}` `{{link}}` `{{reason}}`），后台可编辑
- 同一收件人限流（1 分钟 1 封、1 天 20 封），防滥用与 SMTP 封号
- 发送失败自动重试 1 次并记录日志；连续失败告警（后台提示配置异常）

### 11.5 落地顺序

1. **SMTP 配置页 + 测试发送**（当天，配置即验证）
2. **注册验证（lazy 模式）+ 找回密码**（核心闭环）
3. **存储告急通知（管理员）+ 阈值设置**（运维刚需，先于业务通知）
4. **交易类通知**：VIP 购买成功 / 到期提醒 / 付费图被购买 / 分成结算（随对应功能）
5. **安全类**：审核拒绝、下架、违规警告
6. 运营类（公告订阅）最后
