# AI 审核联动标签体系 · 设计方案

> 状态：**设计稿（未实现）**。实现前再评审一轮，按阶段推进。

## 一、结论

在现有审核链路上扩展输出标签，**改动成本低、收益高**：审核已经调用了视觉模型，让它在同一次请求里多返回 `tags` 字段即可，不增加调用次数。
关键在于**标签必须受控**（否则不可检索、不可统计），以及**双存储**（JSON 快展示 + 关联表快查询）。

## 二、标签体系设计

### 2.1 维度（受控）

| 维度 | 说明 | 示例 |
|---|---|---|
| 主体 | 图里是什么 | 人物 / 动物 / 风景 / 建筑 / 物品 / 文字截图 / 插画 / 表情包 |
| 风格 | 画面风格 | 写实 / 二次元 / 3D / 像素 / 摄影 / 手绘 |
| 用途 | 对用户的价值（图床场景最有用的维度）| 壁纸 / 头像 / 表情 / 素材 / 参考图 |
| 色调 | 画面色调 | 深色 / 亮色 / 多彩 / 单色 |
| 质量 | 可用性 | 清晰 / 模糊 / 低光照 / 有水印 |

### 2.2 数量与结构

- 每次 1~3 个（用户原始设想），建议实现时放宽到 **最多 5 个**（1 个主类 + 至多 4 个辅助）
- 主类（主体）**必选**，其余可空
- 全部来自**受控词表**（约 60 个），模型只允许选词表中的词

### 2.3 受控 vs 自由——三方案对比

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A 完全自由 | 灵活 | 同义词爆炸（"猫咪/小猫/cat"），无法统计 | 否 |
| B 纯受控词表 | 可统计、可筛选 | 词表维护成本高，长尾覆盖弱 | 部分 |
| **C 混合（推荐）** | 主类受控 + 2~3 个自由关键词归一化 | 需要归一化映射表 | **采用** |

归一化规则：小写、去空格、近义词映射（`小猫/咪咪 → 猫`）、长度 ≤ 10 字。

### 2.4 不该生成什么

- **人物身份/人脸特征**（隐私风险）——只描述客观内容（"人物"、"合影"），不出"某人名字/性别/年龄"
- 政治敏感、色情暗示词——审核已有 verdict 负责拦截，标签不承担裁决

## 三、存储设计

```
images
  + tags        JSON    ["猫","插画","壁纸"]       ← 列表/API 直出，避免 JOIN

tags                                            ← 标签字典（统计/合并/词表管理）
  id, name(唯一), slug, category(主体/风格/用途/色调/质量),
  source(auto|user), use_count, status, create_time

image_tags                                      ← 关联表（筛选/统计 JOIN）
  id, image_id, tag_id, source(auto|user), confidence, create_time
  UNIQUE(image_id, tag_id)
```

**为什么双写**：JSON 供列表与 API 零 JOIN 输出；关联表供「按标签筛选图片」「标签排行榜」「某标签的拒绝率」等统计。

## 四、展示位置（按优先级）

| 位置 | 形式 | 说明 |
|---|---|---|
| 后台图片管理 | 新增「标签」列（chips，最多 3 个 + 悬停全量）；筛选栏加标签筛选 | 管理员日常使用主场景 |
| 后台审核 tooltip | 在模型描述下追加 `标签：猫 / 插画 / 壁纸` | 与现有复审原因同一浮层 |
| 前台我的图库 | 卡片底部 chips | 用户侧可见，可点击筛选同标签 |
| 图片详情页（规划中）| 完整标签 + 相关推荐 | 与图片详情页一起做 |
| API 响应 | `data.tags` 数组 | Lsky 兼容不受影响（扩展字段）|
| 后台统计页（规划）| 标签排行榜 / 标签×拒绝率 | 运营决策依据 |

## 五、标签的最大化利用

1. **检索**：`/gallery?tag=猫`、后台「按标签筛选」、API `list?tag=猫`
2. **运营洞察**：标签排行榜（平台最热的图片类型）→ 指导公告/活动/内容推荐；标签×拒绝率 → 找出容易违规的标签组合，反哺审核 prompt 与词表
3. **推荐**：详情页「同标签图片」；图库「你可能喜欢」
4. **SEO**（远期）：图片详情页标签作为关键词、生成标签聚合页
5. **广告定向**（远期）：某类内容页展示对应广告位内容
6. **数据资产**：CSV 导出增加 tags 列（图片导出已有，扩一列即可）
7. **人工修正（主动学习）**：用户/管理员可增删标签 → `source=user` → 用于词表优化与模型 prompt 迭代
8. **容量治理**：标签驱动的批量操作（如"批量冻结所有『低质量』标签的图"）

## 六、实施阶段

| 阶段 | 内容 | 依赖 |
|---|---|---|
| **P1** | 审核 prompt 扩展 tags + 受控词表常量 + `images.tags` JSON + 后台标签列/筛选 + API 返回 + 标签归一化 | 无（当天可完成）|
| **P2** | `tags` 字典表 + `image_tags` 关联表 + 双写 + 统计页（排行榜/拒绝率）| P1 |
| **P3** | 前台图库 chips + 标签筛选页 + 用户手动修正 + 词表管理界面 | P2 |
| **P4** | 详情页相关推荐 / SEO 聚合页 / 广告定向 / 主动学习闭环 | P3 + 详情页 |

## 七、风险与对策

| 风险 | 对策 |
|---|---|
| 模型标签幻觉/漂移 | 受控词表 + temperature 0 + 非法标签直接丢弃 + 每次记录原始输出到审计日志 |
| token 成本增加 | prompt 增加约 30~50 tokens，可忽略；单请求不增加调用次数 |
| 多语言不一致 | 存储统一中文，展示层可映射（词表带 aliases） |
| 旧图无标签 | 后台「批量补标签」任务（复用审核链，分页回填，限流）|
| 隐私与合规 | 禁止生成身份/人脸特征类标签（见 2.4）|
| 标签噪音过多 | P2 起提供词表合并/停用工具；use_count 低的自动归档 |

## 八、本期不做

- 不做标签的自动聚类/向量检索（成本与复杂度高，标签足够用）
- 不做用户自定义标签公开词表（先内部词表，P3 再放开用户修正）
- 不做基于标签的计费/权限（与 Token 计划无关）
